# Integration Test

複数の構成要素を実際に接続し、境界を越えたデータ、状態、エラー、リソースの扱いを検証する。Unit TestやComponent Testの細かな検証を繰り返さず、連携経路と主要なユーザージャーニーに限定する。

## 利用すべき場面

- APIから画面、RepositoryとDatabase、Service間、認証から認可までの流れを検証するとき。
- データの登録・取得・更新・削除、メッセージング、ジョブなどの非同期処理を複数層で確認するとき。
- リリースに重要なログイン、購入、登録、更新などの主要ユーザージャーニーを確認するとき。

## 利用すべきでない場面

- 1つの関数、Model、Serviceの分岐は `unit-test`。
- 1つのUI部品の表示・操作は `component-test`。
- レイアウトや画像の見た目の差分は `visual-regression-test`。
- 本番サービス、本番データ、不要に多数の細かな分岐網羅には使わない。

## 実装ワークフロー

1. 言語、アプリフレームワーク、統合テストランナー、起動方法、CIジョブ、既存のfixture・命名・リセット方針を調査する。
2. テスト対象となるシステム境界、開始条件、成功条件、関係するモジュール・サービス・データストアを図または文章で明確にする。既存テストと重複しない最小の連携経路を選ぶ。
3. 実際に使う依存関係とモック化する依存関係を決める。Databaseにはテスト専用DB、コンテナ、インメモリDBなどを使い、本番サービス・本番データ・未承認の外部送信は使わない。
4. Given / When / Then（または Arrange / Act / Assert）で、正常フローに加えてネットワーク障害、タイムアウト、重複リクエスト、認証・認可失敗、リトライ失敗など境界に重要なケースを選定する。
5. テスト開始前にfixtureと必要な認証情報・データを準備し、テスト終了時にDBレコード、キュー、ファイル、コンテナ、プロセスなどを確実に後片付けする。各テストを独立したデータ・トランザクション・名前空間で実行する。
6. ユーザー操作または公開APIを起点に処理を実行し、コンポーネント間のデータ形式、トランザクション境界、エラー伝播、リトライ、タイムアウト、認証・認可、データ整合性、ロールバックを検証する。
7. 非同期処理は固定時間sleepではなく、メッセージ受信、状態遷移、ジョブ完了、イベント発行など明確な完了条件を、上限付きで待つ。並行実行時の競合、重複処理、再入可能性も必要に応じて検証する。
8. 対象テストを実行し、失敗を発生したシステム境界ごとに切り分ける。アプリ不具合、fixture・環境不足、タイミング依存を分類し、不要な実装変更を避けて修正する。
9. 対象フロー、関連スイート、可能ならFormat、Lint/Analyze、全テストを実行し、再実行して同じ結果になることと環境が汚染されていないことを確認する。

## テスト環境とライフサイクル

- テスト専用DB、コンテナ、インメモリDB、ローカルモックサーバーなど再現可能な環境を使う。
- セットアップ、テスト実行、検証、クリーンアップの責務を分け、失敗時も後片付けが実行される構造にする。
- テストデータはテストごとに識別可能な値を使い、共有アカウント、共有DB、実行順序への依存を避ける。
- 外部依存をモック化する場合も、モックの応答形式とエラーを実際の契約に合わせる。

## 完了条件

- 主要な連携経路と、どのシステム境界を検証したかが明確である。
- テスト専用環境またはテスト専用データを使用し、本番サービス・本番データを使っていない。
- コンポーネント間のデータ形式、整合性、エラー伝播、トランザクション・ロールバックが該当範囲で検証される。
- 認証・認可、リトライ、タイムアウト、ネットワーク障害、重複リクエスト、並行実行を重要度に応じて検討している。
- 非同期処理の完了条件を正しく待機し、固定sleepに依存しない。
- 実行後にデータやリソースが残らず、再実行しても同じ結果になる。
- 失敗時にどの境界で失敗したか分かる診断可能なアサーションになっている。

## 検証方法

- 対象フローを絞って実行し、次に関連スイートを実行する。
- CIと同じ環境・fixtureで複数回、可能なら並行実行して安定性とデータ分離を確認する。
- テスト終了後にDB、キュー、コンテナ、ファイル、プロセスが残っていないことを確認する。
- 実行できない場合は、必要なSDK、コンテナ、サービス、環境変数、認証情報、fixture、権限を列挙し、未検証範囲を報告する。
