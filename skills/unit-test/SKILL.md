# Unit Test

1つの責務を持つ公開された振る舞いを、外部環境から分離して検証する。関数、クラス、値オブジェクト、バリデーション、状態遷移、データ変換、エラーハンドリング、ビジネスルールを対象にし、実装詳細ではなく入力・戻り値・例外・状態変化を確認する。

## 利用すべき場面

- 外部システムに依存しない小さなロジックを高速に検証するとき。
- 関数、クラス、値オブジェクト、バリデーション、状態遷移、データ変換、エラーハンドリング、ビジネスルールを検証するとき。
- 外部依存をモック、スタブ、フェイクに置き換えて、ユニット単体の契約を検証できるとき。

## 利用すべきでない場面

- 実際のDB、API、ファイルシステム、ブラウザ、OSへの接続を検証するとき。
- 複数モジュールをまたぐ実環境に近いテストやユーザーフローは `integration-test`。
- Widget/Componentの描画やユーザー操作は `component-test`。
- 画面レイアウトや画像の見た目の差分は `visual-regression-test`。

## 実装ワークフロー

1. プロジェクトの言語、フレームワーク、テストランナー、実行コマンドを調査する。既存テストの配置、命名規則、モックライブラリ、CI設定も確認する。
2. 対象ロジックを1つの責務に絞り、公開API、入力、戻り値、例外、状態変化、依存関係、既存テストを明確化する。重複するテストは作らない。
3. 対象の契約から、Arrange / Act / Assert（または Given / When / Then）でテストケースを設計する。正常系、異常系、境界値、空値、null、重複値、最大値、最小値を該当する範囲で検討する。
4. DB、API、ファイル、ブラウザ、OS、時刻、日付、乱数、環境変数などの外部・不安定要素を、既存方針に沿ったモック、スタブ、フェイク、固定値、注入可能なClockへ置き換える。
5. 期待する振る舞いがテスト名から分かる命名にし、公開された振る舞いを意味のあるアサーションで検証する。内部メソッド、呼び出し順、私有状態などを必要以上に固定しない。
6. 共有可変状態や実行順序への依存をなくし、各テストが自分で初期状態を準備して単独再実行できるようにする。テストは高速に保ち、不要な待機や重いセットアップを避ける。
7. 対象テストを実行し、失敗を実装・テスト・環境の問題に分類して原因を修正する。プロダクトコードの変更はテスト成立に必要な最小限にする。
8. 対象テスト、関連テスト、可能なら標準のFormat、Lint/Analyze、全テストを実行し、保守性・可読性・実行速度を確認する。

## 完了条件

- 対象ロジックの1つの責務と公開された振る舞いが明確で、主要なケースを網羅している。
- 正常系、異常系、境界値、空値、null、重複値、最大・最小値のうち該当するケースが検証されている。
- 外部環境に依存せず、テストを単独で再実行できる。
- テストが高速に完了し、実行順序や共有状態に依存しない。
- 失敗時に原因が分かる、振る舞いに結び付いたアサーションになっている。
- 対象テストが成功し、実行コマンドと未解決事項を報告できる。

## 検証方法

- まず対象ファイルまたはテスト名を絞ったテストを実行し、単独実行と関連テスト実行の両方を確認する。
- 可能ならテストを複数回または任意順で実行し、状態共有や順序依存がないことを確認する。
- プロジェクト標準のFormat、Lint/Analyze、全テストも実行する。
- 実行できない場合は、検出したテストランナー、実行したコマンド、失敗原因、必要な依存・設定・サービス、未検証範囲を具体的に報告する。
