# Repository Instructions Generator

対象リポジトリの実態に基づく、短く実行可能なエージェント向け指示ファイルを作成または更新する。一般的な開発知識ではなく、確認できたファイル・設定・コマンド・パターンを根拠にする。

## 出力形式と配置の選択

- ユーザーが形式や出力先を指定した場合は、その指定を優先する。`AGENTS.md`、`CLAUDE.md`など、対象形式の既存ファイル・設定・公式仕様に従い、内容を一律に同じ形式へ変換しない。
- 未指定の場合は依頼対象範囲の既存指示ファイルを確認する。候補が1つならその形式と配置を使い、複数なら変更案の作成前に対象をユーザーへ確認する。
- 指定も既存ファイルもなければ、リポジトリルートの `AGENTS.md` を出力先にする。
- 形式・配置の仕様が確認できない場合は推測で作成せず、不明点を確認する。以下の「対象指示ファイル」は、この手順で確定したファイルを指す。

## 権限と安全性

- 最初に `pwd` とリポジトリのルート（通常は `git rev-parse --show-toplevel`）を確認し、調査対象をそのルートに限定する。
- 既存の指示ファイルを先に読み、ルートから対象ディレクトリまでの適用範囲、親子の優先関係、競合を確認する。`AGENTS.md`、`CLAUDE.md`、README、CONTRIBUTING と、ツールが提供する追加指示を対象にする。
- 既存の対象指示ファイルは内容を尊重する。全面置換せず、有効な指示を保持し、重複・矛盾・明らかに古い記述だけを根拠付きで整理する。対象外の指示ファイルや階層別のルールは変更しない。
- 変更前に現在の対象指示ファイルと作成・更新案の差分を確認する。
- ユーザーが明示的に作成・更新を依頼していない場合はファイルを書き換えず、提案内容と差分だけを報告する。明示的な依頼がある場合のみ、対象指示ファイルを編集する。
- 秘密情報、認証情報、個人情報、実値のトークンや鍵を収集・出力・コピーしない。環境変数は名前と用途だけを記載する。

## 調査

次の順序で、存在するものだけを調べる。大規模な出力は必要な行だけ抽出し、ファイルを推測で補完しない。

1. ルートと階層ごとの指示ファイル（`AGENTS.md`、`CLAUDE.md`、利用環境が指定する形式など）、`README.md`、`CONTRIBUTING.md`
2. `package.json`、`pubspec.yaml`、`Cargo.toml`、`pyproject.toml` などの実在する設定ファイル
3. `Makefile`、`Taskfile*`、`justfile`、`scripts/`、package scripts などの開発スクリプト
4. `.github/workflows/`、`.gitlab-ci.yml` などのCI設定
5. formatter、linter、型チェッカー、テストランナー、ビルド設定
6. `lib/`、`src/`、`app/` など主要ソースの構成、命名、依存分離、生成コードの扱い
7. ドキュメントの配置、リンク、生成・公開・更新コマンド
8. テストの配置、命名、fixture/mock方針、実行方法
9. 最近のgit履歴（恒久的なルールの根拠にはせず、現在のファイルと設定で裏付ける）

各記載候補について、根拠ファイルと、確認済みか未検証かを内部で対応づける。複数の証拠が食い違う場合は、優先順位・実行可能な設定・最新の明示的な指示を比較し、解決できなければ `要確認` として分離する。履歴だけ、慣習だけ、ファイル名だけから規約を断定しない。

## 指示ファイルの作成・更新

調査結果から必要な項目だけを記載する。該当情報が存在しない項目は無理に追加せず、判断に影響する不明点だけを `要確認・未検証` にまとめる。記載候補は次のとおり。

- リポジトリの概要、使用言語・フレームワーク・主要ツール
- 主要ディレクトリと責務、実在する開発・ビルド・テスト・lint・formatコマンド
- 確認できた命名・実装パターン、生成ファイルや直接編集禁止ファイル
- 環境変数・外部サービスに関する安全な注意事項
- テストの配置・命名・実行方法
- PR・コミット規約（設定、テンプレート、履歴など明確な根拠がある場合のみ）
- 変更後に実行すべき検証、未検証事項

コマンドは対象形式に適した書式で示し、存在しないディレクトリ・コマンド・規約を作らない。既存ドキュメントやテストの細部を複製せず、対象指示ファイルから参照できる粒度に留める。指示はエージェントがそのまま実行できる具体性にする。

## 実装・ドキュメント・テストの連携

このSkillの作業中に実装変更も依頼されている場合は、実装だけで完了にしない。

- 変更対象に関係するREADME、仕様書、設計書、APIドキュメント、利用方法、開発者向けガイドを調査する。
- 関連ドキュメントが存在する場合は、実装と同じ作業単位で更新し、実装との矛盾を確認する。存在しない文書を不要に新規作成しない。
- 変更内容に最も適した既存テストを特定し、あれば追加・更新する。なければ既存の配置・命名規則に従って新規作成する。
- 正常系だけでなく、影響する異常系、境界値、回帰ケースを検討する。追加・更新したテストを実行し、可能なら全体テストも実行する。
- 実装・ドキュメント・テストの三者に矛盾がないことを確認する。実行できない検証は理由と未検証範囲を報告する。

## 実行と報告

作成・更新後、対象リポジトリで確認できた標準コマンドを優先して、format、lint/analyze、関連テスト、可能なら全体テストとビルドを実行する。コマンドが確認できない場合は推測で実行せず、未検証として扱う。対象指示ファイルの記載が実際のファイル構成・設定・コマンドと一致するか、出力形式・配置が選択した仕様に適合するかを再確認する。

最終報告は簡潔に次の順で示す。

- 調査した主なファイル
- 対象指示ファイルの形式・出力先と、反映した主なルール
- 更新したドキュメント（なければその旨）
- 追加・更新したテスト（なければその旨）
- 実行した検証コマンドと結果
- 未検証事項または要確認事項
