# コミット作業手順

ユーザーが現在の作業のコミット、またはコミット準備を明示的に依頼したときに使用する。

## 手順

1. `git status`、ステージ済み差分、未ステージ差分全体を確認し、依頼対象と対象外を区別する。
2. 変更を論理的な目的ごとに分割する。機能変更、リファクタリング、設定変更、ドキュメント、テストなどを、可能な限り別コミットにする。依存する変更や分割によって壊れる変更は、順序を考慮した最小のまとまりにする。
3. 可能な範囲でリポジトリに記載された検証コマンドを実行する。検証を省略または失敗した場合は、コミット前に明確に伝える。
4. 1つのコミット候補について、意図したファイルまたはhunkだけをステージする。秘密情報、生成物、他のユーザー変更、対象外の削除・整形変更を含めない。
5. `git diff --cached --check`を実行し、ステージ済み差分をもう一度確認する。
6. コミット候補ごとに、対象ファイル、変更目的、コミットメッセージ、検証結果をユーザーへ提示し、実際のコミット前に明示的な確認を求める。確認されていない候補はコミットしない。
7. 承認された候補だけを、簡潔な命令形のメッセージで順番にコミットする。既存の規約があれば従い、なければ`feat:`、`fix:`、`docs:`、`chore:`などの短い形式を使う。
8. 各コミットのハッシュと最終的な作業ツリーの状態を確認する。ユーザーの明示的な依頼なしにpush、amend、履歴書き換えを行わない。
9. コミット後、現在のブランチに関連するPull Requestの有無を確認する。PRがある場合は、今回のコミットによるPRタイトル・本文・検証結果への更新案を作成し、変更箇所をユーザーへ提示する。
10. PR説明の更新はリモート状態の変更であるため、コミットとは別にユーザーの明示的な確認を得てから実行する。確認されなければ、コミットだけ完了し、PRは更新しない。PRがない場合は、その旨を報告する。

依頼範囲が不明確なら、ステージ前に確認する。無関係な変更は保持し、コミット後に別途報告する。ユーザーが「コミットして」とだけ依頼した場合も、コミット候補の提示と確認を省略しない。コミット後のPR更新確認も省略しない。
