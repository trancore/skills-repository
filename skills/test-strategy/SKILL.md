# Test Strategy

変更内容とユーザー要求を分析し、テストレベルの重複を避けながら、必要なテスト種別と不足しているケースを決める。既存テストを先に調査し、テストを実装せず、実装者がそのまま着手できる判断結果を出力する。

## 利用すべき場面

- 新機能、バグ修正、リファクタリング、UI変更に対して、どのテストレベルが必要か判断するとき。
- Unit、Component、Integration、Visual Regressionの責務を整理し、最小限の組み合わせを提案するとき。
- 既存テストの重複を避け、不足しているテストだけを洗い出すとき。

## 利用すべきでない場面

- すでに対象テストの実装方法が決まっており、テストコードを書く作業だけなら該当する個別Skillを使う。
- コードレビュー、性能測定、セキュリティ監査、実装機能そのものの設計が主目的の場合は使わない。

## 判定基準

- 純粋なロジック、値変換、バリデーション、状態遷移、ビジネスルール、エラーハンドリングは `unit-test`。
- 1つのUI部品または1画面内の状態、ユーザー操作、入力、イベント、アクセシビリティは `component-test`。
- 複数モジュール、サービス、Repository、DB、API、認証・認可、非同期処理、主要ユーザージャーニーの連携は `integration-test`。
- 見た目、レイアウト、テーマ、レスポンシブ、多言語表示の意図しない変更は `visual-regression-test`。
- 複数レベルが必要な場合は、各レベルに異なるリスクや契約がある場合だけ組み合わせる。下位テストで十分な分岐を上位テストへ重複させない。

## 実装ワークフロー

1. プロジェクトの言語、フレームワーク、既存テストランナー、テストコマンド、テスト配置・命名規則、モックライブラリ、CI設定を調査する。
2. 要求または変更差分から、変更された責務、ユーザーに見える振る舞い、外部境界、データの流れ、表示状態、回帰リスクを抽出する。推測と確認済みの事実を分ける。
3. 既存テストを検索し、対象・ケース・fixture・snapshotの有無を確認する。既存の保証を再提案せず、不足している観点だけを特定する。
4. 変更された振る舞いを判定表に分類する。純粋ロジック、単一UI、複数構成要素の連携、見た目の変更が重なっていないかを確認する。
5. 各テスト種別について、対象、モック化する対象、実際に使う依存、必要なテストデータ、正常系・異常系・境界値を定義する。日付、時刻、乱数、環境変数、外部サービスなどの不安定要素も指定する。
6. 実行コマンドを既存のランナーとCI設定から特定する。特定できない場合は候補ではなく、未確認であることと必要な追加設定を明記する。
7. 出力を「推奨するテスト種別」「理由」「テスト対象」「モック化する対象」「必要なテストケース」「実行コマンド」「完了条件」「テストしない範囲と理由」の順に整理する。
8. 既存テストと重複する提案、実装詳細に依存する提案、単に網羅率を上げるだけの提案を除外する。

## 判断の補助表

| 変更の性質 | 推奨 |
| --- | --- |
| 入力から戻り値、例外、状態変化を決めるロジック | unit-test |
| 1つの部品の表示、入力、クリック、キーボード、フォーカス | component-test |
| API・DB・Repository・Service・画面などの接続 | integration-test |
| レイアウト、色、フォント、テーマ、レスポンシブ、言語表示 | visual-regression-test |
| ロジックとUI表示の両方が変更された | unit-test + component-test |
| UIからデータ保存や外部境界まで変更された | component-test + integration-test |
| UIの構造と見た目の両方が変更された | component-test + visual-regression-test |
| 複数サービスを含む主要導線と重要画面が変更された | integration-test + 必要なvisual-regression-test |

組み合わせは変更範囲に必要な最小限にし、同じ期待結果を複数レベルで繰り返さない。

## 出力要件

必ず次の項目を含める。

- **推奨するテスト種別**: 優先順位と、単独か組み合わせか。
- **その理由**: 変更された責務・リスクとの対応。
- **テスト対象**: 関数、Component、境界、画面、ユーザージャーニーなど。
- **モック化する対象**: 外部API、DB、時刻、乱数、認証など。実際に使う依存も区別する。
- **必要なテストケース**: 正常系、異常系、境界値、空値、権限、タイムアウト、見た目の状態など該当するもの。
- **実行コマンド**: 対象テスト、関連テスト、可能ならFormat・Lint/Analyze・全テスト。
- **完了条件**: 何が保証されれば完了か。
- **テストしない範囲とその理由**: 既存テストで保証済み、対象外、費用対効果が低いなどの根拠。

各ケースは Arrange / Act / Assert または Given / When / Thenで短く表現し、テスト名や期待する振る舞いが分かる粒度にする。実装者に判断を丸投げする曖昧な「必要に応じて」だけの記述は避ける。

## 完了条件

- 変更内容とユーザー要求が、1つ以上のテストレベルへ根拠付きで分類されている。
- 既存テストを確認し、重複ではなく不足分だけを提案している。
- 推奨種別、理由、対象、モック、ケース、実行コマンド、完了条件、非対象範囲がすべて記載されている。
- テストレベル間の責務が重複せず、提案が変更リスクに対して最小限である。
- 実行コマンドと環境前提が確認済みか未確認か明示されている。

## 検証方法

- 既存テストの検索結果と変更差分を照合し、提案ケースが未カバーであることを確認する。
- 各推奨が判定基準のどれに該当するか確認し、同じ振る舞いを複数レベルへ重複配置していないか確認する。
- プロジェクトのテストランナー、モック方針、CIコマンドと実行コマンドが一致しているか確認する。
- テスト実装を依頼された場合は、このSkillの出力を個別の `unit-test`、`component-test`、`integration-test`、`visual-regression-test`へ引き継ぎ、推奨外のテストは追加しない。
